Q2  1NF/2NF/3NF 与传递依赖
==============================================================================
  未规范化的表（student_id -> dept -> dean，存在传递依赖）：
     (1, 'CS', 'Alice')
     (2, 'CS', 'Alice')
     (3, 'EE', 'Bob')

  异常 ① 更新异常：只改了 CS 系一名学生的 dean 字段
     (1, 'CS', 'Carol')
     (2, 'CS', 'Alice')
     (3, 'EE', 'Bob')
     → 同一个系现在有 2 个不同的 dean，数据自相矛盾

  异常 ② 删除异常：删掉 EE 系唯一的学生
     → EE 系还剩 0 行，「EE 系的系主任是 Bob」这条信息随学生一起丢失了

  分解为 3NF 之后：
     (1, 'CS', 'Alice')
     (2, 'CS', 'Alice')
     (3, 'EE', 'Bob')
     改系主任只需改 _dept_demo 一行；删学生也不会丢掉系主任信息。

  本项目里的对应处理：
     • store_name 只存在 store 表，product 表只存 store_id  → 无传递依赖 ✅
     • orders 存 delivery_address（当时的收货地址），而不是每次去读customer.default_address
       —— 这是**有意保留的冗余**：地址必须保留历史快照，可接受
     • orders.store_id 是冗余列（可由明细推导），为门店统计省一次 join，代价是数据库无法强制一致

Q3  INNER / LEFT / RIGHT JOIN，以及必须用 LEFT JOIN 的场景
==============================================================================
  「每位骑手的配送量，包括没有配送的骑手」
     LEFT  JOIN → 返回 200 位骑手
     INNER JOIN → 返回 180 位骑手  （漏掉 20 位从未配送的骑手）

  「每位顾客的订单数，包括零订单顾客」
     LEFT  JOIN → 5000 位顾客
     INNER JOIN → 4488 位顾客  （漏掉 512 位从未下单的顾客）

  RIGHT JOIN 是镜像写法，本项目没有天然需要它的场景；
  但仍可用它重写骑手配送量（把 orders 放左边）：
     返回 200 位骑手（与 LEFT JOIN 等价，只是表顺序对调）

  反连接（LEFT JOIN ... WHERE IS NULL）用于找「从未……」的记录：
     从未被售出的商品 = 20 个
     没有任何明细的订单 = 0 笔

Q7  GROUP BY / HAVING 与 WHERE 的区别
==============================================================================
  WHERE 在分组之前过滤行：
     连接后总行数                 = 50000
     加 WHERE 排除已取消订单后     = 47569
     → WHERE 先砍掉 2431 行，聚合只在这 47569 行上做

  HAVING 在分组之后过滤组：
     GROUP BY 后得到 4485 个组（每位顾客一组）
     加 HAVING COUNT >= 3 后只剩 4227 组
     → HAVING 过滤的是「组」，WHERE 过滤的是「行」

  把聚合条件写进 WHERE 会报错：
     1111 (HY000): Invalid use of group function

  HAVING 不带 GROUP BY 时，整张表被当作一个组：
     全店累计：订单 47569 笔，营收 14543419.10

Q8  VIEW 与 STORED PROCEDURE
==============================================================================
  ① VIEW：把「门店营收」这个三表连接存成虚拟表
     查询 v_store_revenue（前 5 行）：
       (5, 'Community Fresh Store 05', 2443, Decimal('1579550.80'))
       (4, 'Community Fresh Store 04', 2939, Decimal('1496723.80'))
       (3, 'Community Fresh Store 03', 3393, Decimal('1251728.20'))
       (1, 'Community Fresh Store 01', 10574, Decimal('1130388.30'))
       (2, 'Community Fresh Store 02', 4328, Decimal('1042748.50'))
     → 视图本身不存数据、也不加速查询（MySQL 视图不物化），
       它的价值是把复杂的连接封装起来，并可用于列级权限控制

  ② STORED PROCEDURE：把「下单」这个事务封装成一个调用
     CALL sp_create_order(...) 之后：(900123, 1, Decimal('85.50'), 'pending')
     明细：[(1, 3, Decimal('28.50'))]
     → 订单头 + 明细 + 总额回填 + 事务边界，全部封装在一次 CALL 里

  ③ 两者区别归纳
     视图   = 保存下来的 SELECT，像表一样被查询；用于简化、权限、逻辑独立
     存储过程 = 带参数与控制流的服务端程序，用 CALL 调用；用于业务逻辑与批处理
     简言之：视图「查」，存储过程「做」
